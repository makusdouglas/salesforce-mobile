# Feature Specification: Mandatory Local Lock

**Feature Branch**: `004-local-lock`
**Created**: 2026-04-20
**Status**: Draft
**Input**: User description: "Implement the mandatory local lock per constitution §7 D6. First-run flow forces the salesperson to set a 4–6 digit PIN (stored hashed in expo-secure-store, never plain). Cold-start and post-inactivity (default 5min, configurable) MUST require unlock via biometrics (expo-local-authentication) when available and enrolled, with automatic fallback to the PIN screen on failure or wet-hand/dirty-sensor scenarios. PIN reset path requires full online re-login against Supabase. Local lock is complementary to D5 — it does not replace Supabase auth, only guards casual access to a lost device."

### Design decisions carried into this spec

- **shadcn/ui (light) reuse from 003** — lock and setup screens chain visually from Login. Same card, same wordmark treatment, same primary-black CTA. Forking the palette would create two competing aesthetics on adjacent screens of the same flow.
- **Biometric prompt is OS-owned, not drawn on the canvas** — the OS modal (`expo-local-authentication.authenticateAsync`) is the biometric surface. The Lock frame shows the PIN-pad resting state after biometric was attempted; the "Face ID tentado" pill is a subtle, one-time acknowledgement of the fallback transition (FR-007) without cluttering FR-020's no-business-data constraint.
- **PinPad is a single reusable primitive** — 3×4 grid, 9 digit keys + blank + 0 + backspace. One component, two sizings (phone 56 pt key / tablet 64 pt key). Consumed by both PinSetup and Lock. Promotes to `src/features/lock/components/PinPad.tsx` at implementation time (task T011).
- **Dual pill badges ("Passo 1 de 2" on PinSetup, "Face ID tentado" on Lock)** — subtle state cues that communicate multi-step flow (setup) and fallback-from-biometric (lock) without punctuating the interface with banners. Both use the same muted-pill primitive.
- **"Esqueci meu PIN" is a ghost button below the card, not inside it** — intentionally weak visually to keep the primary path (biometric / PIN) unambiguous. Mirrors 003's Relogin "Cancelar" placement.
- **Lock phone dots show 3 of 6 filled + disabled "Desbloquear"** — the frame captures the mid-entry + minimum-length interaction at a glance. Lock enables "Desbloquear" at ≥ 4 digits (curve in FR-016).
- **PinRecoveryConfirm separates phone (bottom sheet) and tablet (centered dialog)** — same content, two native presentations. Reuses the 003 Relogin modal treatment exactly.
- **"Your field data is safe" reassurance** (FR-015 / US3 scenario 1) is encoded as a dedicated bullet with a `shield` icon inside PinRecoveryConfirm, alongside the "requires internet" bullet (FR-014). Two bullets cover the two fears the salesperson has at that moment: "will this take me offline?" and "will this nuke my work?".
- **No offline-state variant frame** — the offline recovery UI ("Conecte-se à internet para continuar", disabled Continuar) is a deterministic state of the same frame; drawing it separately would add no design information. Same reasoning for the confirm-step of PinSetup and the progressive-delay countdown state of Lock.
- **No extraneous controls** — no "Skip", "Remember me", "Create PIN later", "Change account" affordances. Single-user-per-device (constitution §1) and mandatory-on-first-run (FR-001) lock the scope.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — The Salesperson Sets a PIN Once and Unlocks Daily With Their Finger (Priority: P1)

A salesperson finishes their first-ever online login on the device. Before they can browse the catalog or see any client data, the app walks them through setting a short numeric PIN — type it, confirm it, done. From that moment on, every time they open the app from scratch (cold launch), the app greets them with a lock screen. On a device with biometrics enrolled, the salesperson's fingerprint or face unlocks the app in under a second, without them having to type anything. When the biometric sensor fails — wet hands at a fridge, dirty sensor after handling boxes, or a finger that just won't register this morning — the lock screen falls through to a PIN pad immediately, and the salesperson types the four-to-six digit PIN they set on day one. Either way, the unlock works with zero internet: the device does not phone home to let the salesperson into their own app.

**Why this priority**: This is the core promise of constitution §7 D6 — a device-level guard that protects local catalog and client data from casual access if the phone is lost, left on a counter, or handed briefly to someone else. Without it, the whole argument that D5 "online-one-time" auth is safe (because it keeps a long-lived refresh token on-device) falls apart: the refresh token — and all local business data — would sit behind nothing more than the OS lock screen, which many salespeople in the field leave on a weak PIN or disable entirely. The first cold-start unlock is the user-visible surface of this entire feature; US2 and US3 exist to protect around it.

**Independent Test**: On a freshly installed app, complete an online login, set a 4–6 digit PIN, and confirm. Cold-launch the app with biometrics enrolled and confirm biometric unlock lands on the home screen without network. Separately, dismiss the biometric prompt (or test on a device without enrolled biometrics) and confirm the PIN pad appears, accepts the configured PIN, and lands on the home screen. Repeat both variants with the device in airplane mode — no network call is made during unlock.

**Acceptance Scenarios**:

1. **Given** a fresh install where the salesperson has just completed their first successful online login, **When** the app routes past login, **Then** the app MUST present a PIN setup flow that refuses to continue until the salesperson has typed a 4–6 digit numeric PIN and confirmed it by typing it a second time matching the first.
2. **Given** the salesperson typed a PIN on the first screen and a non-matching value on the confirmation screen, **When** they submit, **Then** the flow MUST surface a clear mismatch message and require them to restart the two-step setup. No partial PIN is saved.
3. **Given** a salesperson with a PIN set and biometrics enrolled on the device, **When** the app is cold-launched (offline or online), **Then** the app MUST present a lock screen that immediately invokes the OS biometric prompt, and on success MUST navigate to the home screen without any network call.
4. **Given** a salesperson with a PIN set but no biometric enrollment (or a device with no biometric hardware), **When** the app is cold-launched, **Then** the app MUST present the PIN entry screen directly — no failed-biometric-prompt flash, no degraded UX — and a correct PIN unlocks the home screen.
5. **Given** a salesperson at the biometric prompt with wet or dirty fingers, **When** the biometric attempt fails or is dismissed by the salesperson, **Then** the lock screen MUST fall through to the PIN entry screen within the same session without requiring the app to cold-launch again.
6. **Given** a salesperson at the PIN entry screen, **When** they type an incorrect PIN, **Then** the screen MUST remain on the PIN entry screen with a clear but non-leaking error ("PIN incorreto") — no navigation, no partial access, no count of wrong attempts revealed in a way that helps guessing.
7. **Given** a salesperson on the lock screen (biometric or PIN), **When** the screen is rendered, **Then** the app MUST NOT reveal any business data behind or around the lock — no catalog previews, no client counts, no sync status, no last-action text. The lock screen is a blank gate.

### User Story 2 — The App Locks Itself If the Phone Is Left Unattended (Priority: P2)

The salesperson steps away from the counter for a few minutes to grab a soda or handle a call from a different customer. When they come back and wake the phone, if enough time has passed, the app greets them with the same lock screen they saw on cold launch — biometrics first, PIN as fallback. If they came back quickly (within the inactivity window), the app is exactly where they left it. The salesperson can configure the inactivity timeout up or down from the constitutional default (5 minutes), within a reasonable range, so a salesperson who visits many stores back-to-back can shorten it and a salesperson who takes long customer meetings can lengthen it.

**Why this priority**: Cold-start unlock (US1) only fires when the app is killed. A phone left on a counter with the app in the background is still logged in and data-readable the moment someone presses the home screen and reopens the app. Constitution §7 D6 explicitly requires an inactivity-triggered lock specifically to close this gap — a phone carried in a pocket and briefly placed down is the realistic theft scenario, not an adversary doing a full cold-launch. P2 because a pilot MVP could technically ship with cold-start lock alone and still satisfy half of D6 for initial validation, but this story MUST ship in the same release as US1 for the feature to be called complete under the constitution.

**Independent Test**: Set the inactivity timeout to 1 minute (or equivalent configurable minimum) to shorten the test loop. With the app unlocked and on the home screen, background the app and wait longer than the timeout, then foreground it — the lock screen MUST appear. Separately, background it and foreground again within the timeout — the app MUST be exactly where it was, with no lock screen. With the app foregrounded and the salesperson actively interacting with it (tapping, typing), no lock MUST trigger regardless of absolute elapsed time. Reset the inactivity timeout to the default (5 minutes) and repeat the background-and-wait variant once to confirm the default applies.

**Acceptance Scenarios**:

1. **Given** an unlocked app on the home screen with the inactivity timeout set to its default, **When** the app is backgrounded for longer than the timeout and then foregrounded, **Then** the app MUST present the lock screen and MUST NOT return to the prior screen until the salesperson unlocks.
2. **Given** an unlocked app on the home screen, **When** the app is backgrounded and foregrounded within the timeout window, **Then** the app MUST return to the exact prior screen with no lock screen shown.
3. **Given** an unlocked app with the salesperson actively interacting (taps, text entry, scrolls), **When** time passes during active interaction, **Then** the inactivity timer MUST reset on each interaction — an actively-used app MUST NOT auto-lock from under the salesperson.
4. **Given** the salesperson is in a settings area that exposes the inactivity timeout control, **When** they adjust it within the allowed range, **Then** the new timeout MUST take effect on the next background-and-return cycle and MUST persist across cold launches.
5. **Given** an unlock via biometrics or PIN after an inactivity lock, **When** it succeeds, **Then** the app MUST restore the salesperson to the exact screen and state they were on before the lock triggered — not to the home screen and not to a refreshed state. Draft orders, scroll positions, and unsaved text in edit fields MUST be preserved.
6. **Given** an unlock fails (wrong PIN, dismissed biometric) after an inactivity lock, **When** the salesperson tries again, **Then** the lock screen MUST remain until a successful unlock. A canceled unlock attempt MUST NOT navigate the app to a neutral screen that leaks what the salesperson was last doing.

### User Story 3 — The Salesperson Forgot Their PIN and Recovers Without Losing Work (Priority: P3)

A salesperson hasn't opened the app in a week and has genuinely forgotten the four-to-six digit PIN they set. On the lock screen they tap "Forgot PIN". The app requires internet — a device-local PIN reset would defeat the entire point of having a PIN — and walks them through a full re-login against the online auth provider, using their normal e-mail and password. After a successful re-login, the app wipes the old PIN, walks them through setting a new one, and unlocks. Every client, every draft order, every payment receipt, every cached catalog image they had on the device before the "Forgot PIN" tap is still there, untouched.

**Why this priority**: PIN recovery is essential for operating the app at realistic scale — humans forget PINs, especially four-digit ones on a professional tool they use for a few hours a day — but a pilot MVP with two salespeople can survive a rollout week without it if the operator (the admin) can talk either salesperson through a manual workaround (full logout-and-login from the admin side, or a reinstall that preserves cloud-synced work). P3 because it is not on the critical path of the first internal pilot, but it MUST ship before handing the app to anyone outside the two-person pilot because support calls scale linearly with salesperson count and this is the single most common support cause for locked-PIN apps.

**Independent Test**: On an app with a known PIN, open the lock screen, tap "Forgot PIN", confirm the app requires internet to proceed, go through the online re-login flow against the auth provider, set a new PIN on the same flow, and confirm the app unlocks on the new PIN. Separately, after the recovery, verify every pre-existing local record (clients, orders including drafts, receipts, catalog cache) is present by opening each screen and counting entries — the count MUST match the pre-recovery count. Separately, attempt the "Forgot PIN" flow with the device in airplane mode — the app MUST block with a clear "connect to the internet" message and MUST NOT unlock, MUST NOT wipe the existing PIN, and MUST NOT alter local data.

**Acceptance Scenarios**:

1. **Given** a salesperson on the lock screen who does not remember their PIN, **When** they tap the "Forgot PIN" affordance, **Then** the app MUST route them into an online re-login flow that requires the same e-mail and password credentials used at initial login.
2. **Given** the "Forgot PIN" flow started with no internet available, **When** the salesperson tries to submit, **Then** the app MUST display a "connect to the internet to continue" message, MUST NOT authenticate offline, MUST NOT wipe the existing PIN, and MUST leave the salesperson on the recovery flow (still locked, offline-blocked).
3. **Given** the salesperson submits valid credentials through the recovery flow with internet, **When** re-login succeeds, **Then** the app MUST wipe the old PIN hash from secure storage and MUST route the salesperson through the same PIN setup flow used on first run (FR-001–FR-004).
4. **Given** the salesperson completes the new PIN setup after a successful recovery re-login, **When** they confirm the new PIN, **Then** the app MUST unlock and land on the home screen.
5. **Given** a "Forgot PIN" recovery just completed end-to-end, **When** the salesperson checks any screen holding local business data (clients list, orders list including drafts, receipts, cached catalog), **Then** 100% of records present before the recovery MUST still be present. Zero records MUST be lost to the recovery cycle.
6. **Given** the salesperson cancels the "Forgot PIN" flow before completing re-login, **When** they return to the lock screen, **Then** the original PIN MUST still be accepted. Starting recovery MUST NOT invalidate the PIN that was there before recovery succeeded.

### Edge Cases

- What happens on a device with no biometric hardware at all (budget Android)? The lock screen MUST default to PIN-only on every unlock. There MUST be no biometric prompt flash and no "use biometrics" affordance anywhere in the UI for that device.
- What happens when the salesperson has biometric hardware but has not enrolled any fingerprint or face in the OS? Same as "no biometric hardware" for the purposes of the lock screen — PIN-only, no prompt. If the salesperson enrolls later, the next cold launch or next post-inactivity unlock picks biometrics up automatically, with no in-app opt-in step required.
- What happens when the salesperson adds a new fingerprint or re-enrolls their face in the OS after the PIN was set? The app continues to accept any OS-verified biometric on the device — the constitution does not require the app to invalidate the PIN on biometric-enrollment change. Adversarial "enroll my own fingerprint on a stolen device" is out of scope for the local-lock layer; server-side revocation (D5) is the recourse.
- What happens when the salesperson taps "Cancel" on the OS biometric prompt? Exactly the same as a failed biometric attempt — the lock screen immediately shows the PIN entry path. The salesperson is never stranded at a dead biometric prompt.
- What happens when the salesperson types a wrong PIN repeatedly? The app MUST apply a progressive delay (slowing down subsequent attempts) to make brute-force guessing infeasible within a reasonable session, and after a threshold of consecutive wrong attempts MUST route the salesperson to the "Forgot PIN" recovery flow (effectively forcing an online re-login). Specific threshold and delay curve are implementation details documented in the plan; a reasonable default is assumed (see Assumptions).
- What happens when the OS locks the biometric sensor after too many failed attempts at the OS level (a known Android/iOS behavior)? The lock screen MUST fall back to the PIN path and MUST NOT propagate the OS biometric lockout as an app-level failure — the salesperson can still unlock with their PIN.
- What happens when the app is cold-launched on a device that never had a successful D5 login (i.e., post-install before first login)? The D5 login screen comes first — D6 cannot present anything because the PIN has not been set yet. The app must NOT require a PIN unlock on a fresh install before first login.
- What happens when the D5 refresh token is rejected in the background while the app is unlocked? Nothing, as far as D6 is concerned — the lock screen is not re-presented. The D5 re-login prompt appears on the salesperson's next network-requiring action per the 003 spec. The two layers are independent (FR-017).
- What happens on D5 logout? The PIN MUST be wiped along with the session credentials (FR-018). The next successful login after logout MUST re-trigger the first-run PIN setup flow (FR-019).
- What happens when the salesperson is actively in a long form (e.g., typing a note on an order) and the inactivity timer is about to expire? Active interaction — taps, typing, scrolling — MUST reset the inactivity timer. Only time during which the app is in the background (or foregrounded but with no interaction, if the plan decides to treat idle foreground that way) counts toward the timeout. The simpler and recommended interpretation is: inactivity timer runs on background time only; foreground time always resets it.
- What happens when the device is unplugged / battery dies / OS kills the app for memory? Next launch is a cold launch, and the cold-start lock applies (US1).
- What happens when the salesperson presses the power button (OS screen lock), then unlocks the phone with the OS PIN or biometric, returning to a still-foregrounded app? The app's inactivity timer is independent of OS screen lock. If the time spent with the screen off did not exceed the inactivity timeout, the app is still unlocked. If it did, the app lock screen appears on return. The OS screen lock does not satisfy the app lock.
- What happens when the salesperson lowers the inactivity timeout to its minimum and is working through a routine that pauses just past the minimum repeatedly? This is an acceptable consequence of a user-chosen short timeout — the lock triggers, the salesperson unlocks with biometrics in under a second, and continues. The MVP does not model "I am in the middle of a sales call" as a reason to suspend the timer.
- What happens when the salesperson uninstalls and reinstalls the app? The PIN hash in secure storage is wiped by the OS on uninstall — the reinstall is effectively a fresh install (US1 scenario 1): first-run D5 login, then first-run D6 PIN setup.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: On the first cold launch after a successful online login (whether fresh install or post-logout re-login), the app MUST present a PIN setup flow and MUST NOT allow the salesperson to reach any business screen until a valid PIN is set.
- **FR-002**: The PIN MUST be a numeric value of 4 to 6 digits. The app MUST reject input outside this range during setup.
- **FR-003**: The PIN setup flow MUST require the salesperson to type the PIN, then type it again on a separate confirmation screen, and both values MUST match exactly before the PIN is accepted.
- **FR-004**: The PIN MUST be persisted only as a cryptographic hash (with a per-device salt) in the operating-system's secure credential storage (Keychain on iOS, EncryptedSharedPreferences on Android, as surfaced by `expo-secure-store`). The plaintext PIN MUST NEVER be written to disk, to logs, to telemetry, to secure storage, or to any other form of persistence.
- **FR-005**: On every cold launch after a PIN has been set, the app MUST present a lock screen before any business screen (catalog, clients, orders, receipts, settings) becomes reachable. The app MUST NOT render business data in any form behind the lock screen.
- **FR-006**: When the device reports that biometric authentication is available AND the salesperson has at least one enrolled biometric credential, the lock screen MUST invoke the OS biometric prompt as the primary unlock path.
- **FR-007**: When biometric authentication is not available, not enrolled, fails, or is dismissed by the salesperson, the lock screen MUST fall through to the PIN entry screen without requiring the app to be restarted and without surfacing any error to the salesperson beyond the normal OS biometric feedback.
- **FR-008**: The lock screen — both biometric and PIN paths — MUST complete unlock with no network round-trip on the happy path. Unlock MUST work with the device in airplane mode.
- **FR-009**: The app MUST track a configurable inactivity timeout with a default of 5 minutes. When the elapsed background time since the last foreground interaction exceeds this timeout, the app MUST transition the session to a locked state and, on the next foreground event, MUST present the lock screen.
- **FR-010**: The inactivity timeout MUST be configurable by the salesperson through an in-app settings control within a reasonable range (see Assumptions for default range). The chosen value MUST persist across cold launches and MUST apply immediately to subsequent background-foreground cycles.
- **FR-011**: Foreground time MUST NOT count toward the inactivity timeout — only time spent in background contributes. The inactivity timer starts when the app transitions to background and is cleared on foreground return (where the expiry check is evaluated). An actively-used or passively-idle foreground app MUST NOT auto-lock from under the salesperson.
- **FR-012**: After a successful unlock following an inactivity lock (not a cold launch), the app MUST restore the salesperson to the exact screen and in-memory state they were on prior to the lock. Unsaved text in edit fields, scroll positions, selected items, and draft order state MUST survive the lock cycle.
- **FR-013**: The lock screen MUST expose a "Forgot PIN" affordance (label: Portuguese, owned by UI implementation per constitution §9) that routes into a PIN recovery flow.
- **FR-014**: The PIN recovery flow MUST require a successful full online re-login against the remote authentication provider (the D5 credentials — e-mail and password). The app MUST NOT provide any device-only PIN reset path. When the device has no internet during recovery, the flow MUST block with a "connect to the internet" message and MUST NOT alter the existing PIN or any local business data.
- **FR-015**: Upon successful PIN recovery re-login, the app MUST wipe the old PIN hash from secure storage and MUST route the salesperson through the PIN setup flow (FR-001–FR-004) to establish a new PIN. Only after the new PIN is set MUST the app unlock.
- **FR-016**: The app MUST apply a progressive delay between consecutive wrong PIN attempts to deter brute-force guessing. After a threshold of consecutive wrong attempts (default and specific curve owned by the plan — see Assumptions), the app MUST force the salesperson into the PIN recovery flow (FR-014) as the only way forward.
- **FR-017**: The local-lock layer (this feature) MUST operate independently of the D5 online-auth session layer. Expiration, rejection, or revocation of the D5 refresh token MUST NOT trigger a D6 lock or invalidate the PIN. Conversely, D6 unlock events MUST NOT alter D5 session state.
- **FR-018**: On D5 logout, the PIN hash and any D6-layer state MUST be wiped from secure storage as part of the same wipe that removes the D5 refresh token.
- **FR-019**: The first successful online login after a logout MUST re-trigger the first-run PIN setup flow (FR-001) — a post-logout install is, for D6 purposes, indistinguishable from a fresh install.
- **FR-020**: The lock screen MUST NOT leak any information about the app's state prior to the lock. No business data, record counts, sync status, last-action text, or screenshot-like previews of the prior screen MUST be visible on the lock screen.
- **FR-021**: PIN change by a salesperson who still remembers their PIN (without going through the "Forgot PIN" recovery) is OUT OF SCOPE for this feature. The MVP supports rotation only through the recovery flow.
- **FR-022**: When the app transitions to background (AppState `active → background | inactive`), the UI MUST be masked at the OS level so the task-switcher / multitasking preview does NOT reveal any business data (catalog, clients, orders, receipts, drafts, cached images). The mask MUST be removed automatically on foreground return. This requirement is complementary to FR-020: FR-020 governs the in-app lock screen, FR-022 governs the OS-owned snapshot that sits between a legitimate salesperson's "press home" and the lock-gated return.

### Key Entities

- **PIN credential**: the hashed form of the salesperson's 4–6 digit PIN, persisted in the device's secure credential storage. Conceptually holds the hash, the per-device salt, and the hash-algorithm parameters. Never holds, and never accepts a query returning, the plaintext PIN. Wiped on D5 logout and on successful "Forgot PIN" recovery.
- **Unlock-session state**: in-memory, non-persistent flag indicating whether the current foreground app session is unlocked. Cleared on cold launch, cleared on inactivity-timeout expiry, set on successful biometric or PIN unlock. Never written to disk.
- **Inactivity configuration**: the salesperson-chosen timeout in minutes within the allowed range, persisted across cold launches in regular app preferences (not a secret). Default: 5 minutes.
- **Failed-attempt counter**: in-memory counter of consecutive wrong PIN attempts in the current session, used to drive the progressive delay in FR-016. Resets on successful unlock or on PIN recovery. Not persisted across cold launches (a cold launch gives the salesperson a clean attempt window, because progressive delay only needs to stop brute-force within a session).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A salesperson can complete first-run PIN setup (enter PIN, confirm, save) in under 30 seconds on a mid-range Android device, starting from the PIN setup screen rendering.
- **SC-002**: On a cold launch with biometrics enrolled, the time from app-tap to interactive home screen is under 3 seconds on a mid-range Android device on the happy path.
- **SC-003**: On a cold launch with biometrics unavailable or not enrolled, the time from app-tap to interactive home screen after a correct PIN entry is under 5 seconds on a mid-range Android device.
- **SC-004**: In a 5-minute scripted offline session covering cold launch, unlock, and routine business work, the number of network calls made by the unlock layer is exactly zero.
- **SC-005**: After an inactivity-triggered lock with the salesperson mid-way through a draft order, unlocking returns the salesperson to that same draft order with 100% of its in-memory state preserved (fields filled, items added, scroll position). No measurable "refresh" or jump to home MUST be observable.
- **SC-006**: On a device without biometric hardware or enrollment, the unlock flow lands directly on the PIN entry screen in 0 additional steps — no biometric prompt flashes, no "biometrics unavailable" dialog, no opt-out required.
- **SC-007**: A filesystem and secure-storage audit conducted immediately after a PIN setup finds the PIN present only in hashed form. Zero entries contain the plaintext PIN, a reversible encoding of it, or any derivative from which the plaintext can be recovered without the salt and the hash-algorithm secret.
- **SC-008**: A brute-force test that submits 1,000 random 4-digit PIN values against the lock screen fails to unlock the app within 10 minutes of continuous attempts on a mid-range Android device (progressive delay + forced-recovery threshold together cap achievable attempt rate).
- **SC-009**: End-to-end "Forgot PIN" recovery (tap Forgot PIN → online re-login → new PIN setup → unlock) completes in under 90 seconds on a mid-range Android device with a broadband Wi-Fi connection.
- **SC-010**: After a "Forgot PIN" recovery, 100% of local business records (clients, orders including drafts, order items, payment receipts, cached catalog) present before recovery remain present after. Zero records MUST be lost across 20 scripted recovery cycles.
- **SC-011**: Across 100 scripted foreground-background cycles with a mix of durations above and below the inactivity timeout, the lock screen triggers correctly on 100% of cycles whose background duration exceeded the timeout, and triggers on 0% of cycles whose background duration was shorter than the timeout.
- **SC-012**: In the OS task-switcher / multitasking preview, an audit on both iOS and Android of 10 representative screens (catalog list, catalog detail, client detail, new-order draft, order detail, receipts list, receipt detail, home, settings, PinSetup mid-flow) shows a masked thumbnail — no business content readable — for 100% of screens on a mid-range device.

## Assumptions

- The online authentication provider used by the PIN recovery flow (FR-014) is Supabase Auth, via the same credential contract as the D5 online-one-time-auth feature (spec 003). This feature does not re-evaluate or re-engineer the online auth layer — it reuses it.
- The device-side local-auth and secure-storage primitives are `expo-local-authentication` and `expo-secure-store` (constitution §3 Mandatory Stack, added in constitution v0.2.0 for §7 D5/D6). This feature does not re-evaluate those choices.
- The 003 online-one-time-auth feature is landed or landing alongside this feature. This feature's FR-014 (full online re-login for PIN recovery) and FR-019 (re-trigger PIN setup after re-login) cross into the 003 surface area; 003 owns the login-screen mechanics and this feature invokes them.
- The 002 local-data-layer (WatermelonDB) is landed so that local business data exists for D6 to be worth guarding. D6 is a gate on top of data — without local data there is nothing to lock.
- The PIN is numeric-only. Constitution §7 D6 uses the word "PIN" (not "passcode" or "password"), which both implies numeric-only and enables the "digits keyboard" on-device for speed (constitution UX1 — "tap, not type"). Alphanumeric secrets are out of scope.
- The PIN hash is produced by a modern password-hashing algorithm (e.g., argon2id, scrypt, or bcrypt) with a per-device random salt. The specific algorithm and parameters are a plan-level decision, not a spec-level one; the spec's requirement (FR-004) is only that the plaintext PIN is not recoverable from the persisted representation.
- The progressive delay and forced-recovery threshold referenced in FR-016 default to a reasonable curve (e.g., no delay for the first 3 attempts, 1-second delay from attempt 4, 5-second delay from attempt 6, route to recovery at attempt 10). Specific numbers are a plan-level decision; the spec's requirement is the shape (progressive → forced recovery).
- The inactivity-timeout configurable range defaults to a reasonable window — e.g., minimum 1 minute, maximum 30 minutes — around the constitutional default of 5 minutes. The exact range is a plan-level decision.
- The "inactivity timer runs on background time only; foreground time always resets it" interpretation is the MVP contract. Any foreground-idle auto-lock behavior (e.g., "salesperson left the app open on the home screen for 10 minutes without tapping") is out of scope — the salesperson is assumed present when the app is foreground.
- Biometric-enrollment changes on the device (new fingerprint added, face re-enrolled) are trusted by the app. The constitution's local-lock layer protects against casual access, not against an attacker with enough time to re-enroll a biometric on a stolen device. Server-side session revocation (D5) and Supabase Row Level Security are the recourse for determined-adversary scenarios.
- Screen copy (labels, error messages, "Forgot PIN" affordance, empty states) is in Portuguese per constitution §9; the UI implementation owns the exact strings. The spec defines semantics (what each state communicates), not copy.
- Automated testing priorities follow constitution §9: business-logic and security tests (hash correctness, plaintext non-persistence, inactivity-timeout calculation, forced-recovery threshold, no-network-on-unlock) rank above UI automation of the lock screens. Lock-screen UI verification is manual during MVP.
- Tablet and phone viewports (constitution §5 UX5) both receive lock-screen and PIN-setup-screen designs when the Pencil design hook runs for this feature. This spec does not constrain the visual design; it constrains behavior.
- The "Forgot PIN" recovery flow visually reuses the D5 re-login screen (from spec 003) or presents a similarly minimal screen that collects the same credential inputs. The exact screen reuse vs. duplication is a plan-level decision; the spec requires only that the credentials and server round-trip are the D5 contract (FR-014).
